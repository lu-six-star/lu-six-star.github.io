数据结构（四）：结构体内存对齐 —— padding 就在你眼皮底下

struct { char c; int i; } 的 sizeof 是多少？字段加起来明明只有 5 字节，实测却是 8——中间 3 个字节的 padding 就藏在 c 和 i 之间。本篇用 6 个结构体的实测数据，把对齐规则每一条钉死。

一、为什么需要对齐

CPU 访问内存按”自然宽度”取数：int 要一次取 4 字节，double 要一次取 8 字节。如果 int 横跨两个 4 字节边界，CPU 要读两次再拼接——对齐就是用空间换访问速度。嵌入式更极端：部分架构（如老 Cortex-M0）未对齐访问直接 HardFault。

三、三条对齐规则（全部被实测验证）

  1. 成员对齐数：int→4、double→8、char→1；嵌套结构体按其内部最大对齐数；
  2. 成员摆放：偏移必须是对齐数的整数倍，放不下就在前面补 padding；
  3. 总大小补齐：结构体总大小必须是最大对齐数的整数倍（尾部也可能补）。

逐个验证：

  • B（8 字节）：c 在偏移 0，i 要对齐到 4 → 偏移 03 补 3 字节 pad，i 占 47；
  • C（24 字节）：d 要对齐到 8 → c 后补 7 字节，d 占 8~15，c2 占 16，尾部补齐到 24；
  • D（8 字节）：i 占 03、c 占 4、s 要对齐到 2 → s 占 67，总 7 补齐到 8；
  • E（16 字节）：嵌套的 B 按对齐数 4 摆放 → c1 占 0、pad 13、b 占 411、c2 占 12，补齐 16。

手写优化结论：同一批字段，{int, short, char, char} 按大小件在前排列 = 8 字节；乱序排 = 12 字节。批量结构体（1 万条记录）调整一次顺序就省 40KB。

四、pack(1)：关掉对齐的代价

#pragma pack(1) 强制紧凑排列，sizeof 从 8 变 5。用途：通信协议打包（字段必须按字节流严丝合缝）。代价：

  • 成员可能横跨对齐边界，部分架构访问要拆成多次总线操作；
  • 未对齐访问在某些 CPU 上直接 HardFault；
  • 所以工程惯例是”发送前 pack 打包，内存里还是自然对齐的结构“，而不是全程 pack。

五、踩坑记录

  1. 口算偏移——协议结构体永远用 offsetof() 确认字段偏移，别跟编译器赌；
  2. 结构体直接 memcpy 跨机器传输——两端对齐/端序不同就解出乱码，协议序列化要用显式字节序；
  3. **以为数组元素是”名义大小”**——B[2] 占 16 字节，每个元素都带自己的 padding；
  4. sizeof 出现在网络传输里——不同编译器/位宽的结果可能不同，跨平台结构体要显式定宽类型（uint32_t）+ pack。

六、小结与下一篇预告

  • 对齐三条规则 + 一个实测表：1、8、24、8、16、5 全部钉死；
  • 字段按大小件在前排列可以白捡内存；
  • offsetof 是协议/驱动开发的必备工具；
  • pack(1) 是协议打包工具，不是内存布局的常态。
