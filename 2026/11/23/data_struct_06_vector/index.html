数据结构（六）：数组与动态数组 —— 手写简易 vector

静态数组大小编译期定死，运行期才知道要多少怎么办？答案就是”动态数组”——容量不够就翻倍扩容。本篇手写一个 40 行的简易 vector，连续 push 17 个元素，亲眼看它扩容四次、数据整体搬家，顺便理解为什么”扩容后旧指针全部失效”。

二、实验：连续 push 17 个元素

实测输出（节选）：

三个实测结论：

  1. 扩容时机精确：容量 0→4→8→16→32，恰好在第 1、5、9、17 次插入时触发——“满了才扩，一次翻倍”；
  2. 每次扩容地址都变：0590 → 2920 → E0D0 → 1F70——realloc 不是原地扩展，是”找新家 + 整体搬迁”；
  3. 数据完好：17 个元素按序无缺——搬迁时 realloc 内部做了完整拷贝。

三、从实测读出的三条工程法则

  1. 扩容后旧指针全部失效——这解释了为什么 C++ 标准规定”vector 扩容后迭代器失效”，也解释了为什么不要长期保存 vector 内部数据的指针；
  2. **均摊 O(1)**：单次扩容要拷贝 O(n)，但翻倍策略让 n 次插入的总拷贝量 ≤ 2n——这就是 C++ vector “push_back 均摊常数”的数学来源；
  3. 能预估就预留：已知要存 1 万条就先扩到 1 万，避免四次搬家——C++ 的 reserve()、FreeRTOS 队列”创建时定深度”，都是同一个权衡。

四、踩坑记录

  1. realloc 返回值直接赋回原指针——失败返回 NULL，原块地址被覆盖就泄漏了（第 3 篇踩过），必须用临时指针承接；
  2. 扩容后继续用旧指针——实测地址全变，旧指针读到的是已释放的内存；
  3. 容量翻倍的起点——从 0 开始首次扩到 4，别从 1 开始翻倍（前几次扩容太频繁）；
  4. 缩容——本实现的容量只涨不缩，长期波动场景可以加”size < cap/4 时减半”策略（std::vector 也从不自动缩容）。

五、小结与下一篇预告

  • 动态数组 = 指针 + size + cap 三个字段 + 翻倍扩容策略；
  • 实测：17 次 push 触发 4 次搬家，地址全变、数据完好；
  • 均摊 O(1) 的代价是”搬家期间旧引用失效”；
  • 数组的痛点也浮出水面了：中间插入/删除要整体挪动——这正是链表登场的原因。
