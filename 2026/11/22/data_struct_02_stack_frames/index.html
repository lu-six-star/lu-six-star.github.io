数据结构（二）：栈与函数调用 —— 栈帧、递归与爆栈

上一篇画了内存地图，这一篇聚焦地图上最活跃的区域——栈。函数调用的”幕后账本”就是栈帧：局部变量、参数、返回地址全在里面。本篇最有看点的实验：我们真的让程序爆栈了，并抓到了 Windows 的退出码 0xC00000FD。

一、函数调用时，栈上发生了什么

每次函数调用，系统在栈顶压入一个栈帧，里面装着：

  • 函数的局部变量和临时数据；
  • 传入的参数（部分走寄存器，多余的压栈）；
  • 返回地址——函数结束后回到哪一行继续；
  • 被调用方要保存的寄存器。

函数返回时，整个栈帧一锅端掉——栈指针回退几字节就是”释放”。这就是栈内存快的原因：分配和释放只是移动栈指针，没有任何 malloc/free 的开销。也是它危险的原因：栈的大小有上限（Windows 默认约 1MB），用超了就爆。

四、栈帧尺寸怎么估、爆栈怎么防

项目 本机实测/规则
每层递归栈帧 ~80 字节（32B 数组 + 返回地址 + 寄存器）
Windows 默认栈 1MB（链接器 /STACK 可调）
理论极限深度 1MB ÷ 80B ≈ 13000 层
嵌入式参考 RTOS 任务栈常为几 KB，递归要更加节制

防护三板斧：

  1. 深递归改循环（或显式用堆模拟栈）——日志类递归转 while + 队列；
  2. 巨型缓冲区改堆分配——char buf[1MB] 挪到 malloc；
  3. Windows 上用链接器 /STACK:reserved,commit 调整栈限，Linux 用 ulimit -s。

五、踩坑记录

  1. 返回局部变量的地址——栈帧已弹掉，指针悬空；要么传缓冲区进来，要么 malloc（第 3 篇）；
  2. printf 带缓冲——crash 时缓冲丢失，长跑日志务必 setvbuf(stdout, NULL, _IONBF, 0)（本系列所有实验的第一行）；
  3. 爆栈不等于优雅退出——它是进程级崩溃，catch 不住（Windows 需 SEH 专门处理），防御靠设计而不是靠捕获；
  4. 嵌入式更敏感：FreeRTOS 任务栈常只有几 KB，第 3 篇实测一个任务连 TCB 带栈才 736 字节——递归在 RTOS 任务里几乎是禁忌。

六、小结与下一篇预告

  • 栈帧 = 局部变量 + 参数 + 返回地址 + 寄存器，随函数调用压栈、返回弹栈；
  • 栈向下生长实测：每层约 80 字节，1MB 栈 ≈ 13000 层递归极限；
  • 爆栈退出码 0xC00000FD 实锤——递归深度必须设计，不能靠运气；
  • 栈是”自动的”，但也是”有上限的”——需要大块、长寿命的内存时，就要请出堆。
