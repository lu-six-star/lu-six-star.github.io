数据结构（一）：C 程序的内存地图 —— 你的变量都住在哪

学数据结构”容易忘”，多半是内存模型没打通——不知道数据住在哪、谁分配谁释放，链表的指针绕两圈就晕。所以这个系列第一篇不谈任何数据结构，先把地基打好：一张 C 程序的内存地图。全文实验均在 Windows + gcc 下真机实测，输出都是本机真实地址。

一、一段 C 程序编译之后，内存被切成六块

区域 装什么 谁管理 生命周期
.text 代码段 机器指令、函数体 编译器 程序全程，只读
.rdata 只读数据 字符串字面量、const 全局 编译器 程序全程，只读
.data 已初始化数据 初值非零的全局/static 编译器 程序全程
.bss 零值数据 未初始化的全局/static 启动代码清零 程序全程
堆 Heap malloc 出来的对象 你（程序员） 从 malloc 到 free
栈 Stack 局部变量、函数调用帧 编译器自动 函数进出

核心区别一句话：**.data/.bss 全程存在，栈上的随函数生死，堆上的由你负责**。

读地址就是读地图：

  1. .text/.rdata/.data/.bss 全部挤在 0x00007FF7_C319xxxx 一族——这是 exe 被映射进内存的区域，彼此只差几十 KB；
  2. 堆在完全另一段地址（0x0000014C_Cxxx），离 exe 区十万八千里——堆是运行时向系统单独要的；
  3. 栈在更高处（0x00000010_xxxx）——它也有自己独立的一段；
  4. g_zeroed[0] 的值是 0：.bss 段在程序启动时被自动清零——这就是”全局变量不初始化也不怕”的底层原因。

三、三个立刻能用上的结论

  1. **”为什么全局变量不初始化是 0，局部变量却是垃圾值？”**——全局住 .bss，启动代码负责清零；局部变量住栈上，那块内存只是”上一位住户留下的痕迹”，没人替你清。
  2. **”为什么改 const/字符串字面量会崩溃？”**——它们在 .rdata 只读段，写它触发访问违例。
  3. **”静态局部变量为什么函数退出后还活着？”**——static 让它从栈搬到 .data 段，生命周期升级为程序全程。

四、踩坑记录

  1. 栈上返回局部变量的地址——函数返回后那块栈帧作废，指针变成悬空野指针（第 2 篇细说）；
  2. 把大数组开在栈上——char buf[1MB] 大概率直接爆栈（默认栈只有约 1MB，第 2 篇实测）；
  3. 堆内存忘记 free——堆不自动回收，泄漏累积（第 3 篇实测 128MB 泄漏的代价）；
  4. 以为 sizeof 数组能拿到动态大小——.bss/.data 的大小编译期就定死，运行期容量要靠堆。

五、小结与下一篇预告

  • 内存地图六分区：代码只读、数据三段（data/bss/rdata）、堆手动、栈自动；
  • 地址族就是身份：0x7FF7 一族是程序本体，0x14C 是堆，0x10 是栈；
  • .bss 自动清零、堆由你管、栈随函数伸缩——三种生命周期对应三种变量。
