FreeRTOS 学习笔记（六）：中断管理 —— FromISR 与延迟中断处理

中断是 RTOS 深水区的入口：中断服务程序（ISR）不在任何任务的上下文里，它活在另一套规则之下。本篇讲清楚两件事——为什么 ISR 只能调用 FromISR 后缀的 API，以及”中断只做标记、任务干活”的延迟中断处理思想。最妙的是，Windows 仿真移植层自带真实的中断模拟，我们可以不碰硬件就把这套机制跑通。

一、中断为什么是另一套世界

任务切换、队列入队、信号量计数……这些内核操作的底层都依赖”关中断 + 任务级上下文”的保护。而 ISR 本身就运行在中断上下文里：

  1. 它不属于任何任务——没有自己的栈帧可以”挂起”，内核的阻塞机制对它完全不适用。ISR 里调 vTaskDelay()？直接死给你看；
  2. 它打断了内核的原子操作。普通 API 进入时会临时关中断保护自己，而 ISR 里再调普通 API，等于在”门已经锁上”的时候又要动里面的东西——真机上的典型后果是随机崩溃；
  3. 它必须快。ISR 不结束，比它低的所有中断和任务都干等。

所以 FreeRTOS 的规矩是：ISR 里只允许调用 FromISR 后缀的 API，并且只做最少的事。

二、延迟中断处理：中断只做标记，任务干活

正确姿势是上图的三段式：

  1. ISR：收数据（读寄存器/DMA 缓冲），然后调一个 FromISR API 把”有事件了”这个消息发出去（入队、给信号量、发任务通知），紧接着退出——前后几十微秒；
  2. 内核：发现 ISR 唤醒了更高优先级的任务，中断一退出就切换过去；
  3. 处理任务：被唤醒后接手所有重活——解析、运算、转发，随便阻塞。

这就是延迟中断处理（Deferred Interrupt Processing）：把”快”留给中断，把”全”留给任务。

  • event #1 里的 1 是通知计数（ulTaskNotifyTake 的返回值）——如果 ISR 在处理任务来不及响应时连续触发，计数会累加，一条通知也能代表多次事件，不丢事件。

五、FromISR 家族速查

任务版 中断版 用途
xQueueSend() xQueueSendFromISR() 入队
xSemaphoreGive() xSemaphoreGiveFromISR() 给信号量
vTaskNotifyGive() vTaskNotifyGiveFromISR() 发任务通知（计数）
xTaskNotify() xTaskNotifyFromISR() 发任务通知（带值）

它们与任务版的差别只有一个：不做任务级的上下文切换（切换的请求通过 portYIELD_FROM_ISR 转述给内核，由”退出中断”这个动作代为执行）。这正是 ISR 语境下唯一安全的做法。

六、踩坑记录

  1. ISR 里调 printf、vTaskDelay、非 FromISR API——前两个会拖垮实时性甚至死锁，最后一个真机直接崩。记住口诀：ISR 只收数据和发通知。
  2. **忘记 portYIELD_FROM_ISR**。功能不丢（被唤醒的任务最迟在下一个 tick 也会运行），但延迟从微秒级劣化到毫秒级——高实时场景就是事故。
  3. FromISR 与任务版 API 混用同一对象是允许的（队列两边都能用），但 ISR 侧只能用 FromISR 版本；反过来任务里用 FromISR 版本是未定义行为。
  4. 中断优先级配置是真机专属话题。Cortex-M 上 configMAX_SYSCALL_INTERRUPT_PRIORITY 之上的中断禁止调用 FreeRTOS API——仿真环境感知不到它，上真机前务必查移植层文档。
  5. 仿真测不出中断延迟。本实验的 5~43ms 波动全部来自 Windows 调度，别把它当性能数据。

七、小结与下一篇预告

  • ISR 不属于任何任务：不能阻塞、不能调普通 API、必须快；
  • FromISR 后缀 = 不做任务级切换的内核 API，配合 portYIELD_FROM_ISR 优雅交接；
  • 延迟中断处理 = 中断只收数据发通知，重活交给被唤醒的任务——既快又全；
  • Windows 仿真的中断模拟（vPortGenerateSimulatedInterrupt）让我们零硬件验证了全链路。
