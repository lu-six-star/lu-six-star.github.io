FreeRTOS 学习笔记（四）：调度器与时间管理 —— tick 心跳与周期任务的正确写法

每个 FreeRTOS 任务都想占用 CPU，谁说了算？答案是一个 1ms 跳动一次的”心跳”——tick。这一篇我们钻进调度器的节拍里，并用两个真机实验回答一个高频面试题：周期任务到底该用 vTaskDelay 还是 xTaskDelayUntil？ 答案是数据给出的：一个周期漂移 30%，一个分毫不差。

一、tick：调度器的心跳

真机上，tick 由一个硬件定时器产生（Cortex-M 上是 SysTick）；在我们用的 Windows 仿真里，它由多媒体定时器模拟（还记得第 2 篇架构图里 port.c 的职责吗？tick 中断正是它的两大工作之一）。configTICK_RATE_HZ=1000 意味着每 1ms 进一次中断。

每次 tick 中断，内核会做三件事：

  1. tick 计数 +1——xTaskGetTickCount() 返回的就是它；
  2. 检查延时列表：vTaskDelay 到期的任务被移回就绪态；
  3. 同优先级时间片轮转：若有同优先级任务就绪，触发一次切换。

而调度器重新挑任务的时机，除了 tick 中断，还有：任务调用了阻塞类 API、调用了 taskYIELD()、任务优先级被改变。这就是为什么第 3 篇实验里，高优先级任务不需要等 tick 到来就能立刻抢到 CPU——唤醒一个高优先级任务的 API 调用本身就触发调度。

二、抢占式、协作式与时间片

上图是一台单核机器上两个任务的完整一生，三个关键行为都在里面：

  • 抢占：1000ms 处 H 的延时到期，tick 中断把它放回就绪态；调度器瞬间选中它，L 的执行被”拦腰截断”——从 L 被打断到 H 开跑，只隔一次上下文切换（微秒级）。这由 configUSE_PREEMPTION=1 控制（默认推荐）；
  • 就绪 ≠ 阻塞：被抢走的 L 回到的是就绪态，不是阻塞态——它没有在等任何事件，只是在排队等 CPU。这一点很多人第一反应会搞错；
  • 时间片轮转：同优先级的任务（如第 3 篇实验 2 里同为优先级 1 的两个任务）由 tick 每 1ms 轮换一次，由 configUSE_TIME_SLICING=1 控制。

反过来，若把 configUSE_PREEMPTION 设为 0，调度器退化为协作式：只有任务主动让出（阻塞、yield）时才切换。裸机思维的”大家自觉”模式，高优先级任务也抢不动了——除非你真的清楚自己在做什么，否则保持默认的抢占式。

原因藏在 vTaskDelay 的语义里：它是相对延时——从”调用时刻”起算 1000 tick。于是周期 = 干活的 300ms + 延时的 1000ms = 1300ms，比设计目标多出 30%。单看一个周期不多，但漂移是累积的：跑 10 个周期，采集时刻已经推后了整整 3 秒。对一个”每秒采集一次”的系统，第 10 次采集实际发生在第 13 秒——日志时间戳、控制周期、通信心跳全部失真。

三个使用要点：

  1. xLastWakeTime 在循环外只初始化一次，之后由 xTaskDelayUntil 内部自动更新——每次循环前手动重置反而会破坏节拍；
  2. 它有返回值（pdTRUE/pdFALSE）：如果干活时间超过周期，节拍已经错过，函数不再等待、立即返回 pdFALSE——这既不是 bug 也不是死等，是明确的”来不及了”信号；
  3. API 改名史：FreeRTOS V10.4.0 之前它叫 vTaskDelayUntil()（很多老教程和书里是这个名字），之后更名为 xTaskDelayUntil() 并增加返回值。内核源码注释里写得明明白白：”vTaskDelayUntil() is the older version of xTaskDelayUntil()”——本篇实验用的是 v11 内核，所以是新名字。

五、怎么选？

写法 语义 适用场景
vTaskDelay(ms) 从现在起休眠 ms 毫秒 一次性等待、响应后歇口气、不在意精确周期的场合
xTaskDelayUntil(&last, period) 下次唤醒锁定在绝对节拍上 一切严格周期任务：采样、控制环、通信心跳、日志轮转

一句话判断：周期起点应该跟着”上次开始”走，还是跟着”这次结束”走？ 前者用 Until，后者用 Delay。

六、踩坑记录

  1. pdMS_TO_TICKS 可能算出 0。它是整数乘除：ms * configTICK_RATE_HZ / 1000。若 tick 频率只有 100Hz（10ms 一跳），pdMS_TO_TICKS(5) 结果是 0——vTaskDelay(0) 的语义是 yield 而不是延时！低 tick 频率下务必检查换算结果。
  2. xLastWakeTime 初始化一次就够。它记录的是”上次唤醒的绝对时刻”，在循环外初始化、由 API 内部维护；在循环里反复重置会让节拍退回相对延时模式。
  3. 干活时间必须小于周期。xTaskDelayUntil 不补课：节拍错过就放弃等待。如果 300ms 的活涨到 1100ms，周期自然保不住——这是设计约束，不是内核的错。
  4. tick 域精确 ≠ 真实时间精确。本篇两个实验的输出数字零抖动，是因为忙等和延时都以 tick 计数为准；但第 2 篇已经实测过，仿真里 1000 个 tick 的真实时长约 1.015 秒。逻辑周期看 tick，物理性能靠真机。
  5. 别误关抢占。configUSE_PREEMPTION=0 的协作式模式下，实验 4 时序图里”H 醒来立刻抢占”的场景不会发生——高优先级任务也得排队等低优先级任务主动让出。默认值 1，别动它，除非你有充分理由。

七、小结与下一篇预告

本篇钻进了调度器的节拍：

  • tick 每 1ms 心跳一次，驱动计数、唤醒、时间片轮转三件事；
  • 抢占式调度下，高优先级任务被唤醒的瞬间就能得到 CPU（时序图完整推演）；
  • 两个真机实验给出铁证：vTaskDelay 做周期任务**周期漂移 +30%**（1300 tick/周期），xTaskDelayUntil 分毫不差（1000 tick/周期）；
  • 记住那道选择题：跟着”上次开始”走用 Until，跟着”这次结束”走用 Delay。
