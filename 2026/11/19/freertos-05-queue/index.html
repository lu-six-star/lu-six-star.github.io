FreeRTOS 学习笔记（五）：队列 —— 任务间通信的第一选择

从这一篇开始，任务和任务之间要”说话”了。裸机时代我们用全局变量传数据，在 RTOS 里这是头号大坑——竞态、轮询、无通知三宗罪。队列一次解决全部问题。本篇三个真机实验，把”队列满了怎么办”和”队列空了怎么办”这两个最高频的疑问用数据钉死。

一、先说说全局变量为什么不行

裸机时代传数据的标准姿势：一个全局数组 + 一个写标志位。放到 RTOS 里，三宗罪立刻暴露：

  1. 竞态：两个任务同时读写同一个变量，没有保护，数据随时被撕裂——你可以用开关中断硬扛，但那是把内核级责任背到自己身上；
  2. 轮询：接收方只能循环查标志位，要么忙等烧 CPU，要么加延时丢实时性；
  3. 无缓冲：生产快、消费慢时，旧数据直接被覆盖，连”来不及处理”的机会都没有。

队列（Queue）一件工具解决三件事：数据的传输（拷贝进队列）、任务的同步（有数据就唤醒接收者）、流量的缓冲（深度兜住速度差）。而且这一切都在内核临界区保护下完成——多个任务甚至中断同时操作同一个队列，也不会竞争。

二、队列长什么样

创建一个队列只需要一句话：

  • 深度 5：最多缓存 5 条数据，满了之后再入队就要看”超时参数”的脸色；
  • 单元 4 字节：每条数据的大小。队列传递的是数据的拷贝——xQueueSend 把你的变量逐字节复制进队列，xQueueReceive 再复制出来。这个设计让队列天然避免了”数据归谁”的问题，代价是大数据拷贝开销（踩坑环节细说）。

核心 API 就三个，全部支持”超时参数”：

API 行为 队列满/空时
xQueueSend( q, &item, timeout ) 数据拷贝入队尾 满：按 timeout 等空位
xQueueReceive( q, &buf, timeout ) 从队首拷贝出数据 空：按 timeout 等数据
xQueuePeek( q, &buf, timeout ) 看队首但不取出 同 Receive

超时参数三档，语义完全不同：

取值 含义 典型场景
0 不等，立即成功或立即失败 绝不能等的场合（如定时器回调里）
pdMS_TO_TICKS(n) 最多阻塞 n 毫秒 有界等待 + 失败降级
portMAX_DELAY 无限期阻塞直到成功 事件驱动的强依赖

阻塞期间任务进入 Blocked 态，CPU 让给其他任务——不是忙等。这是队列”同步”能力的来源：数据一到，内核把等待者唤醒，数据由内核拷贝给它。

非阻塞发送加满队列 = 默默丢数据。如果你的系统只是打了几条日志，无所谓；如果丢的是传感器采样、通信帧，这就是事故。

四、实验 7：阻塞发送 = 自动背压，零丢失

把超时参数从 0 换成 portMAX_DELAY，其他一行不改：

8 秒统计：sent 19，FAILED 0，got 16（还有 3 条在队列里等着被停止时刻截断）。最关键的是：sent 的编号 1、2、3……19 完全连续，一条不少。

注意看节奏的变化：前 4 条在队列吃满之前飞快入队（tick 2、66、129、193），之后每一条 sent 都等到了消费者腾出空位才成功——队列自动把生产者节流到消费者的节奏。这就是”背压（back-pressure）”：生产快消费慢的矛盾没有消失，而是被转化为生产者的阻塞等待，数据零丢失。

两种写法没有绝对对错，是一道设计选择题：这条数据丢了会怎样？ 丢得起（日志采样）用非阻塞，丢不起（控制指令）用阻塞，两边都不沾就用”有界超时 + 失败降级”。

8 秒统计：empty 32 次、got 7 次。两个细节值得咂摸：

  • 接收成功的时刻（1002）正好对齐生产节拍——数据一入队，内核立刻唤醒阻塞中的消费者，毫秒都不用多等；
  • 两次唤醒之间的 800ms 里，消费者睡在 Blocked 态，每 200ms 醒来看一眼纯属本实验的日志需要。若把超时换成 portMAX_DELAY，消费者会一路睡到数据到达，一次都不白醒。

对照裸机的”轮询 + 延时”方案：同样的功能，这里没有一次忙等、没有一次无效唤醒，CPU 的空闲时间全部交还给了空闲任务。

六、队列深度怎么定？队列集是什么？

深度设计没有公式，只有权衡：太浅——突发流量一来就满（丢数据或背压节流）；太深——占内核堆内存，且掩盖”消费太慢”的设计问题。实用做法：先用理论突发量估算，跑起来后用 uxQueueMessagesWaiting() 观察实际水位再调。

队列集（Queue Set）：让一个任务同时阻塞等待多个队列/信号量的机制，xQueueCreateSet() 创建、xQueueAddToSet() 归组。能省任务数，但增加复杂度——初学阶段知道有这东西即可，多数场景用”每个队列一个任务”更清晰。

七、踩坑记录

  1. 传指针的坑（本篇最大的坑）：sizeof(uint32_t) 的队列传的是值拷贝，安全；一旦队列单元改成 sizeof(char *) 传指针，就要保证指针指向的内存在被取出前始终有效——指向发送任务栈上局部变量的指针，等消费者拿到时那块栈早就被别的数据盖掉了。要么传静态/堆内存，要么干脆传值。
  2. 大块数据别硬拷贝。队列单元开 1KB，每条消息入队出队各拷 1KB，还全在临界区里。大块数据用指针队列 + 内存池，或用 stream_buffer。
  3. 队列满不是异常，是设计题。背压（阻塞发送）、丢数据（非阻塞）、有界超时降级，三选一必须显式设计。还有个特殊工具：深度 1 的队列 + xQueueOverwrite()，永远只留”最新值”——适合”发送最新传感器读数”场景。
  4. portMAX_DELAY 慎用。如果日志队列满导致日志任务永久阻塞，而每个任务都写日志——一串任务连环堵死。关键路径上的队列给有界超时，失败走降级逻辑。
  5. 中断里必须用 FromISR 版本。本篇实验都在任务上下文里，所以用 xQueueSend()；中断服务程序里必须换 xQueueSendFromISR()——参数、语义都不同，硬用任务版在真机上会出诡异崩溃。这正是下一篇的主题。

八、小结与下一篇预告

本篇把队列的”满”与”空”都钉死在了数据上：

  • 队列 = FIFO + 值拷贝 + 内核临界区保护，一己之力解决传输、同步、缓冲；
  • 超时三档 0 / 有界 / portMAX_DELAY 是三种完全不同的设计取舍；
  • 实验 6：非阻塞 + 满 = 86% 数据丢失；实验 7：阻塞发送零丢失 + 自动背压；实验 8：空队列阻塞等待，CPU 一点不烧。
