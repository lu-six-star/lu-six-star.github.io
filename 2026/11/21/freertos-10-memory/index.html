FreeRTOS 学习笔记（十）：内存管理 —— heap_1 ~ heap_5 五种方案怎么选

configTOTAL_HEAP_SIZE 声明的 128KB，在系统启动后真正可用的只剩 128448 字节——剩下 2624 字节被谁花掉了？创建一个队列、一个任务各要多少字节？任务删除之后内存真的收回来了吗？本篇用两个水位计 API 把这些账全部实测清楚，并把 heap_1 ~ heap_5 五种堆方案的选型一次讲完。

一、为什么 FreeRTOS 不用标准库 malloc

嵌入式里直接用 C 标准库的 malloc/free 有三个先天风险：实现不透明（碎片行为不可预测）、不线程安全（要自己加锁）、速度不确定。FreeRTOS 的答案是自带一个小而确定的堆：

  • 你用 configTOTAL_HEAP_SIZE 声明一块静态数组当堆（本系列是 128KB）；
  • xTaskCreate、xQueueCreate 这些动态创建 API 内部调用 pvPortMalloc/vPortFree——内核对象全部从这块堆里出；
  • 五种官方实现 heap_1 ~ heap_5，二选一参与编译，行为各不相同。

选型口诀：不会释放选 1，要释放选 4，内存不连续选 5——想用标准库 malloc 再考虑 3。绝大多数项目从 heap_4 起步（释放 + 相邻空闲块自动合并，本系列 demo 全用它），这也正是第 3 篇里”任务删除后由空闲任务回收内存”能成立的前提。

二、实验 14：给堆装两个水位计

FreeRTOS 提供两个现成的水位计（声明在 portable.h）：

  • xPortGetFreeHeapSize()：当前剩余；
  • xPortGetMinimumEverFreeHeapSize()：历史最低剩余——它是”系统最紧张时刻”的体检报告，调堆大小的第一依据。

探针任务按顺序执行：记录基线 → 创建队列（10×4B）→ 创建任务（70 字栈）→ 删除任务 → 等空闲任务回收 → 记录。实测输出：

五条数字，五段知识：

  1. 基线就少了 2624 字节（131072 − 128448）：调度器启动时已经创建了空闲任务、定时器服务任务（daemon）和命令队列，加上探针任务自己——内核对象都在这块堆里；
  2. 一个深度 10、单元 4 字节的队列花 200 字节：存储区只有 40 字节，剩下 160 字节是队列结构体、链表和事件列表——队列的”房租”比”仓库”贵；
  3. 一个 70 字栈的任务花 736 字节：栈 70×4=280 字节（第 3 篇说过单位是字），任务控制块 TCB 占约 456 字节；
  4. 删除任务后 +736，精确复原：空闲任务把 TCB 和栈释放回堆，heap_4 与相邻空闲块合并成功——第 3 篇”空闲任务打扫卫生”的说法有了实数；
  5. 历史最低 127512：说明系统最紧张时刻也还有 127KB 富余，128KB 的堆对本实验绰绰有余——反过来讲，如果这个数字逼近 0，就是扩堆的明确信号。

三、栈溢出检测：给最危险的故障装烟雾报警器

任务的栈是固定大小的，写穿了就破坏相邻内存——嵌入式最阴险的故障。FreeRTOS 提供两级烟雾报警器（configCHECK_FOR_STACK_OVERFLOW）：

  • 1：每次上下文切换检查栈指针是否越界——快，但只能抓”已经越界”的；
  • 2：检查栈末尾的填充图案（0xA5A5A5A5）是否被改写——能抓”即将越界”，代价是多一点切换开销。

触发时内核调用钩子 vApplicationStackOverflowHook()，你可以在里面打印肇事任务名然后停机。本系列为了实验纯粹把它设为 0，真机项目请务必开 2。配套的调栈工具是 uxTaskGetStackHighWaterMark()——任务历史上栈的最深使用量，比”拍脑袋”定栈深科学得多。

四、踩坑记录

  1. 单位陷阱再强调：栈深度参数是”字”。Cortex-M 上 1 字 = 4 字节，128 是 512 字节；Win32 仿真里 configMINIMAL_STACK_SIZE = 70 只是因为真实栈在 Win32 线程里——仿真数字不能照抄到真机（第 3 篇的账：仿真任务实测 736 字节，其中 TCB 占大头）。
  2. 创建 API 返回值必须检查。堆不够时 xTaskCreate 返回 pdFAIL、xQueueCreate 返回 NULL——不检查的话，后面所有针对这个任务的调用全在解引用空指针。开 configUSE_MALLOC_FAILED_HOOK=1 再加一层保险。
  3. heap_2 的碎片是隐形的。它释放但不合并，长期”分配-释放-分配”之后，明明总空闲够、却找不到一块连续空间——图为证（本篇配图 heap_2 行）。要释放就上 heap_4。
  4. 堆不是万能池。大块、生命周期复杂的数据缓冲建议自己管理内存池或用 stream_buffer；频繁 malloc/free 小对象则要考虑预分配——堆水位长期抖动就该警惕碎片。
  5. 水位计本身有开销吗？xPortGetFreeHeapSize 是查变量，接近零开销；MinimumEver 同理。它们适合打进日志、看门狗或 CLI 命令里常态化监控——本篇实验就是模板。

五、小结与下一篇预告

  • 五种堆方案一句话：1 只发不收、2 发收但碎片、3 包标准库、4 合并碎片（默认）、5 多段内存；
  • 两个水位计 API 把内存账查得清清楚楚：队列 200 字节、任务 736 字节、删除后精确回收；
  • “历史最低水位”是调堆大小的第一依据，栈溢出检测 + 栈水位是真机项目的标配保险；
  • 单位是字、返回值要查、碎片看 heap_2——内存管理的三条铁律。

系列最后一篇是综合实战：把十一篇的积木——xTaskDelayUntil 周期采样、队列、事件组报警、软件定时器心跳——拼成一台完整的多任务数据采集系统，跑出真实的系统日志。另外还有一个预告过的翻车复盘：xTimerStart 放在 main() 里静默失灵的完整现场。收官见。
