FreeRTOS 学习笔记（八）：事件组与任务通知 —— 更轻量的同步方式

队列和信号量解决”传数据”和”通知一下”，但还有两类更细的需求：**”好几个条件都满足才开工”（多条件同步）和“就是叫你一声，顺带捎个 32 位数”**（点对点轻量通信）。前者归事件组，后者归任务通知——它们是 FreeRTOS 同步工具箱里最轻的两件。照例全部真机实测。

一、事件组：32 个开关管住”多条件”

事件组（Event Group）就是一个 32 位整数（configUSE_16_BIT_TICKS 为 0 时），每一位是一个事件标志：

  • xEventGroupSetBits(eg, BIT0)：把某位置 1（可从中断用 FromISR 版本）；
  • xEventGroupWaitBits(eg, bits, ...)：阻塞等待若干位——bits 之间的逻辑关系可选 AND（全置位才醒）或 OR（任一置位就醒）；
  • xEventGroupSync()：WaitBits 的加强版——设置自己的位 + 等别人的位一步完成，且全员到齐时自动清零，天生就是”同步屏障”。

它解决的核心问题是多任务同时同步：A、B、C 三个任务各自干活，谁都别轮询谁，全员就绪的那一刻一起放行。

三、任务通知：每个任务自带的”邮箱”

任务通知（Task Notification）是 V8.2 引入、之后不断加强的轻量机制：每个任务天生自带一个 32 位通知值 + 若干通知状态位，不需要创建任何内核对象就能收发：

官方给的量级描述是：解锁一个任务，任务通知比二值信号量快约 45%，且更省 RAM——因为通知直接住在任务控制块里，没有独立的队列结构、没有额外的内存分配。

这五行日志里藏着一个一眼看上去像 bug 的细节：接收方的打印比发送方还早 23ms（302 < 325）。

这不是乱序，而是调度器的正常表现：发送任务的优先级（1）低于接收任务（2），xTaskNotify() 执行完的瞬间接收方就被唤醒并抢占运行——它打印完、处理完，发送方才轮到打印自己的日志。日志顺序由调度决定，tick 才是真相：value=10 的通知发生在 tick 302 前后，一切自洽。

这个实验也顺便演示了 eSetValueWithOverwrite 的语义：直发覆盖。如果接收方处理太慢，旧值会被新值覆盖——**任务通知是”邮箱”不是”队列”**，只有一个格子。

五、怎么选？一张表

需求 首选工具 理由
多条件同时满足才继续（AND） 事件组 WaitBits 位组合 + 阻塞等待
多任务互相同步（都到齐再走） 事件组 Sync 原生屏障语义
一对一发事件/带值唤醒 任务通知 最快、最省、零创建
多任务消费同一条数据流 队列 FIFO + 多方共享
中断→任务通知事件 二值/计数信号量或任务通知（FromISR） 第 6 篇的延迟中断处理
保护共享资源 互斥量 第 7 篇的优先级继承

六、踩坑记录

  1. eSetValueWithOverwrite 会静默覆盖。接收方忙别的时，连发的通知只剩最后一发的值——要”条条必达”请用队列；要”只关心最新值”，覆盖反而是特性。
  2. xTaskNotifyWait 的清除时机。第二个参数是”退出前清除哪些位”，全 1（0xFFFFFFFFUL）表示取走即清；不清的话旧通知会让下一次 Wait 立即返回，看起来像”闹钟坏了”。
  3. 事件组的位要全局规划。事件组是共享对象，两个任务不小心用同一个位，会出现”谁把我的标志清了”灵异事件——按位分工写进注释。
  4. **xEventGroupSync 的返回值是”到齐时刻的全部位图”**，它顺便告诉你其他人都带了什么来——常常比”知道放行了”更有用。
  5. 通知接收者只有一个。任务通知是任务私有邮箱，没有”广播”能力——广播请用事件组。

七、小结与下一篇预告

  • 事件组 = 32 个事件位 + AND/OR 等待 + 原生同步屏障；实测三任务到达差 1096ms，释放差 2ms；
  • 任务通知 = 任务自带邮箱，零对象创建、直发 32 位值，官方口径比信号量快约 45%；
  • 一个”假 bug”讲透了优先级与日志顺序：tick 才是真相，日志顺序由调度决定。
