FreeRTOS 学习笔记（九）：软件定时器 —— 让回调按时到达

系统里总有十几个”每 N 秒干一次某事”的小闹钟：心跳、喂狗、日志轮转、状态上报。给每个闹钟开一个任务太奢侈——软件定时器用一个后台任务统管所有闹钟，到点替你执行回调。本篇有一个特别的看点：一个我们在写这个系列时真实踩到的坑——xTimerStart 放错位置，定时器静默失灵，一条日志都不出。

一、软件定时器不是中断，是 daemon 任务代跑的回调

对定时器的一切操作（Start/Stop/ChangePeriod/Reset）都不会直接动定时器，而是变成一条命令排进定时器命令队列；真正管闹钟的是内核自动创建的定时器服务任务（Timer Service / daemon）：

  • 它阻塞等待命令队列，顺带计算最近的到期时间；
  • 定时器到期，它就执行你的回调函数——注意，回调跑在 daemon 任务的上下文里，不在中断里；
  • 好处：回调里可以调用阻塞 API、不占用中断时间；代价：精度受 tick 与 daemon 调度影响，且回调绝不能阻塞——它一卡，所有定时器集体迟到。

原因藏在启动顺序里：定时器命令队列是由 vTaskStartScheduler() 内部的 xTimerCreateTimerTask() 创建的。在调度器启动之前调用 xTimerStart，命令要排队的队列还不存在，发送失败——而返回值没检查，于是静默失败，完美错过一切报错机会。

四、API 速查与精度讨论

API 行为
xTimerCreate(名, 周期, autoReload, ID, 回调) 创建（此刻不计时）
xTimerStart / xTimerStop 启动 / 停止
xTimerChangePeriod(t, 新周期, timeout) 改周期并立即重新计时
xTimerReset(t, timeout) 重新上弦——常用于喂狗/闲置检测
pvTimerGetTimerID / vTimerSetTimerID 一个回调服务多个定时器时的区分手段

精度讨论：软件定时器的回调时机 = tick 精度 + daemon 的调度延迟。第 4 篇的结论在这里同样适用——严格的周期性要用 xTaskDelayUntil + 专属任务；软件定时器的定位是”一批不严格的低频闹钟”，省下的是任务栈和任务数。高频硬实时（如 PWM 生成）请用硬件定时器。

五、踩坑记录

  1. 调度器启动前调用任何定时器 API 都会静默失败（本篇翻车现场）——命令队列尚未创建。返回值一定要检查。
  2. 回调里阻塞 = 全部定时器陪葬。daemon 单线程，一个 vTaskDelay 或慢 IO 让所有闹钟集体迟到。重活发队列给工作线程（第 5 篇的生产者-消费者模式）。
  3. 回调没有任务参数。多个定时器共用一个回调时，用 pvTimerGetTimerID() 区分是谁在响——ID 在创建时指定。
  4. 精度天花板是 daemon。configTIMER_TASK_PRIORITY 太低，daemon 抢不到 CPU，所有定时器漂移；太高又可能干扰关键任务。按系统权衡配置（还有 configTIMER_QUEUE_LENGTH 与 daemon 栈深度）。
  5. “每 X 毫秒做某事”有两个工具：软件定时器（回调，省任务）vs 周期任务 + xTaskDelayUntil（第 4 篇，精确）。回调里不做重活时用定时器，周期敏感或耗时任务用专属任务。

六、小结与下一篇预告

  • 软件定时器 = 命令队列 + daemon 任务代跑回调；一切操作都经过队列，一切回调都在 'Tmr Svc' 上下文（实测铁证）；
  • 自动重载周期触发、单次触发即停、xTimerChangePeriod 立即按新周期重计——全部实测验证；
  • 回调必须短小，daemon 串行执行会让迟到的回调继续迟到（Auto 2 的 24ms）；
  • 系列亲历翻车：xTimerStart 放在 main() 里静默失败，挪进任务恢复正常。
