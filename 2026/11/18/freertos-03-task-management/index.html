FreeRTOS 学习笔记（三）：任务管理 —— 状态机、优先级与空闲任务

任务（Task）是 FreeRTOS 里最小的调度单位，上一篇我们只是”会用”了 xTaskCreate 和 vTaskDelay，这一篇把任务的一生彻底讲透：它有哪些状态、优先级到底怎么影响调度、以及为什么”空转延时”是 RTOS 大忌。全文三个实验，继续真机实测。

一、任务状态机：一个任务的一生

FreeRTOS 的任何时刻，一个任务必然处于这四个状态之一：

状态 一句话解释 还占用 CPU 吗
就绪 Ready 万事俱备，只差 CPU——随时能跑，在排队 否
运行 Running 正在占用 CPU 执行 是
阻塞 Blocked 主动等待：延时未到、事件没来 否
挂起 Suspended 被人为暂停，不参与调度，除非被唤醒 否

驱动状态切换的就是上图里的几个 API，一张表看全：

转换 触发者 典型 API / 事件
诞生 → 就绪 你 xTaskCreate() 成功返回
就绪 → 运行 内核 调度器选中（当前最高优先级）
运行 → 就绪 内核 / 你 时间片用完、被高优先级抢占、taskYIELD()
运行 → 阻塞 你 vTaskDelay()、等待队列/信号量/事件（第 5~8 篇）
阻塞 → 就绪 内核 延时到期、等待的事件发生
运行 → 挂起 你 vTaskSuspend()
挂起 → 就绪 你 vTaskResume()
任意 → 消亡 你 vTaskDelete()

阻塞和挂起的区别值得单独强调：阻塞的任务有”闹钟”——延时到了或事件来了会自动回就绪；挂起的任务没有闹钟，不调用 vTaskResume() 就永远沉睡。

两个任务优先级同为 1，各跑 8 秒，对比上一版（vTaskDelay）的实测数据：

版本 8 秒打印行数 打印节奏 CPU 状态
vTaskDelay 版 16 行（每秒各 1 行） 规整的 1 秒一次 大部分时间空闲
空转”延时”版 434 行（每任务 217 行） 约 37ms 一次，节奏完全失控 两个任务轮流吃满 CPU

实测输出（节选）：

tick 从 2、3 直接跳到 42——第一次空转”延时”只”延”了不到 40ms。这就是空转的本质问题：

  • 它不产生任何阻塞。任务从”运行”切出去的唯一途径没了，调度器只能靠时间片在两个任务之间硬切，CPU 时间被打印和空转瓜分；
  • 延时精度取决于循环次数，编译器优化等级一变（我们还开着 -O0），”延时”立刻变味；
  • 在单核 MCU 上，这意味着低优先级任务和中断响应全被挤压——下一节的实验三会把这一点演示到极致。

结论：RTOS 里的”延时”必须用阻塞类 API（vTaskDelay），让出 CPU 的同时让内核接管时间。 空转循环不是延时，是烧 CPU。

三、优先级规则：两条铁律 + 一个实验

FreeRTOS 的调度规则可以压缩成两条铁律：

  1. 高优先级抢占低优先级：只要高优先级任务就绪，低优先级立刻让路；
  2. 同优先级按时间片轮转：轮流上场，每人一个 tick（configUSE_TIME_SLICING=1 时）。

实验 3：高优先级忙等 = 低优先级消失

把两件事叠加：TaskB 优先级 2 + 空转忙等（永不阻塞），TaskA 优先级 1 + vTaskDelay。直觉上 A 应该每秒还能挣扎打印一次？

实测 6 秒：TaskB 打印 311 行，TaskA 出现 0 次。一行都没有。

原因就藏在状态机图里：TaskB 永远不阻塞、永远就绪，而它的优先级比 A 高——调度器的铁律 1 决定了 A 根本轮不到上场。连优先级 0 的空闲任务都失去了执行机会。这就是经典问题：低优先级任务被饿死（Starvation）。

设计原则由此而来：

  • 高优先级不是”重要性奖励”，而是”紧急程度声明”；
  • 能阻塞的任务才配得上高优先级——事件驱动的设计（等到事件再干活）是第 7 篇的主题；
  • 永不阻塞的高优先级任务 = 系统其余部分的死刑判决书。

四、空闲任务：优先级 0 的幕后员工

调度器启动时，内核会自动创建一个空闲任务（Idle Task）：

  • 优先级固定为 0（tskIDLE_PRIORITY），是全系统最低；
  • 只要有任何用户任务就绪，它就不跑——所以它天然是”CPU 还有没有活干”的探测器；
  • 它承担着重要的内核事务：回收被 vTaskDelete() 删除的任务的内存（任务自己删自己时，TCB 和栈不能当场释放，只能留给空闲任务打扫）；
  • 可以通过空闲钩子 vApplicationIdleHook（configUSE_IDLE_HOOK=1）做低优先级后台杂务，也是低功耗统计的基础（tickless 低功耗模式是进阶话题）。

实验三里 A 和空闲任务双双消失，正是因为系统里再没有”CPU 空闲”的时刻。反过来说，vTaskDelay 版本里每秒大部分时间 CPU 都在跑空闲任务——这就是”让出 CPU”的真实去向。

五、任务生命周期管理的常用 API

API 作用 备注
xTaskCreate() 动态创建：内核从堆里分配栈和 TCB 本系列默认用法
xTaskCreateStatic() 静态创建：你提供栈和 TCB 内存 需要 configSUPPORT_STATIC_ALLOCATION=1；功能安全场景（禁止运行时 malloc）必备
vTaskDelete() 删除任务，传 NULL 表示删自己 删除自己后内存由空闲任务回收
vTaskSuspend() / vTaskResume() 挂起 / 恢复 挂起无超时，只能手动恢复
vTaskPrioritySet() / uxTaskPriorityGet() 运行时改 / 查优先级 实验 3 的解药之一
vTaskDelay() / vTaskDelayUntil() 相对 / 绝对周期延时 区别是第 4 篇主角
xTaskGetTickCount() 当前 tick 计数 本篇实验输出里的数字来源

关于动态 vs 静态：本系列前几篇都用动态创建，直观省事；但它依赖内核堆（configTOTAL_HEAP_SIZE）。在安全关键项目里通常强制静态创建——所有内存在编译期确定。两种方式创建出来的任务在调度上没有任何区别。

六、踩坑记录

  1. 栈深度单位是”字”不是字节。Cortex-M 上 1 字 = 4 字节，128 就是 512 字节栈；而 Win32 仿真里任务真实栈属于 Win32 线程，70 这个数字不能照抄到真机。真机上拿不准就先用 uxTaskGetStackHighWaterMark() 观测。
  2. **任务函数永远不要 return**。返回是未定义行为；要结束任务用 vTaskDelete(NULL)。
  3. “优先级高 = 重要”是危险直觉。实验三已经证明：把忙等任务设为高优先级，系统其余部分全部饿死。正确姿势是”干活越少、响应越急的任务，优先级越高”。
  4. vTaskDelay(0) 是合法操作，语义是主动让出 CPU 一次（yield），常用于同优先级任务间的礼貌协作。
  5. 任务名不必唯一，也不参与调度，它只活在调试器和统计信息里——但请认真起名，vTaskList() 排查问题时全靠它。

七、小结与下一篇预告

本篇用三个真机实验搞清楚了任务的一生：

  • 四状态状态机：只有运行态占 CPU，其余状态都在”等”；
  • 空转延时是 RTOS 大忌：节奏失控（434 行 vs 16 行）+ CPU 满载；
  • 两条调度铁律 + 一个血泪实验：高优先级忙等 = 低优先级饿死（0 次）；
  • 空闲任务是系统的”呼吸”：它在跑，说明你把 CPU 让对了。
