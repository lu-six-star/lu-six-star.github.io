FreeRTOS 学习笔记（二）：在 Windows 上跑起 FreeRTOS —— 环境搭建与第一个任务

学 RTOS 最劝退的一步往往是”要买块开发板”。其实 FreeRTOS 官方就提供了 Windows 移植层——不用任何硬件，一个 gcc 就能在电脑上跑起真实的 FreeRTOS 内核。本篇所有代码和运行输出都是在本机实测的，照着敲即可复现。

一、Windows 仿真是怎么回事？

上一篇文章说过，FreeRTOS 内核分为”与硬件无关的核心”和”与硬件相关的移植层”。既然如此，那把移植层写成”适配 Windows 的版本”，内核不就能在 Windows 上跑了吗？

官方正是这么做的。FreeRTOS-Kernel 仓库的 portable/MSVC-MingW/ 目录下有一套 Windows 移植层，它的实现思路非常巧妙：

  • 每个 FreeRTOS 任务 = 一个真正的 Win32 线程。任务阻塞时，内核用 Windows 的挂起/恢复机制切换线程，完美模拟”上下文切换”；
  • tick 心跳 = 用 Windows 多媒体定时器（winmm）模拟周期性中断。

对照上图，这就是”本系列路线”那条路：你的代码 → 内核 API → 内核核心 → port.c → Win32。要强调的一点是：Windows 不是实时系统，所以仿真环境里测不出真实时性能，但内核的调度行为、API 语义与真机完全一致——用来学内核，再合适不过。

逐段拆解：

1. 任务函数的”标准形态”。 vPrinterTask 是一个参数为 void *、返回值为 void 的函数，主体是 for( ; ; ) 死循环。这就是 FreeRTOS 任务的标准长相：任务不能 return——返回了内核会直接判定为严重错误。想让任务”结束”，要调用 vTaskDelete(NULL) 删除自己（后面讲任务管理的篇章细说）。

2. 两个任务共用同一个函数，秘密在参数。 在 FreeRTOS 的眼里，任务 = 任务函数 + 独立的栈 + 任务控制块。同一个函数配上不同的 pvParameters，就能实例化出两个互不干扰的任务——这个技巧在传感器轮询等场景非常好用。

xTaskCreate 的六个参数值得一表：

参数 本例取值 含义
任务函数 vPrinterTask 函数入口地址
任务名 "TaskA" 调试用可读名，不必唯一
栈深度 configMINIMAL_STACK_SIZE 单位是”字”不是字节；仿真下任务真实栈在 Win32 线程里，70 足够
参数 (void *)"TaskA" 传给任务函数的指针
优先级 1 数字越大优先级越高，0 最低
任务句柄 NULL 需要后续操作该任务时传入指针拿句柄

返回值是关键：pdPASS 表示创建成功；其他值通常意味着堆内存不够了。

3. vTaskDelay(pdMS_TO_TICKS(1000))。 这是 RTOS 版的”延时”——和裸机的 delay_ms 忙等完全不同：调用后任务进入阻塞态，内核立刻去运行别的任务，1 秒后 tick 中断把它叫醒。pdMS_TO_TICKS 把毫秒换算成 tick 数（我们的 tick 是 1ms 一次，所以换算后就是 1000）。

4. vTaskStartScheduler() 之后，main 不再是主角。 调用它的瞬间，内核创建空闲任务、启动 tick、开始调度，控制权一去不回。main 里写在它后面的代码只有一种情况会被执行：调度器启动失败（几乎总是堆不够）。

每个工程都必须提供一个 FreeRTOSConfig.h——它决定内核哪些功能参与编译、tick 多快、堆多大。基于官方模板（examples/template_configuration/）精简后，本实验用的版本：

初学阶段不用逐个啃完，先记住四个最常用的：

  • configTICK_RATE_HZ：心跳频率，1000 = 1ms 一次；
  • configTOTAL_HEAP_SIZE：内核堆大小，任务创建失败九成是它太小；
  • configMAX_PRIORITIES：可用优先级数量；
  • configASSERT：断言宏，参数传错时原地停机，挂上调试器就能定位——强烈建议开发期始终开启。

其余项”先照抄，用到再查”，官方每个宏都有文档说明。

六、读懂这 9 行输出，你就读懂了”多任务”

现象 1：两个任务在”同时”打印。 宏观上它们并行运行，微观上是内核在两个 Win32 线程间快速切换——这正是第一篇对比图里说的调度器行为。

现象 2：TaskA 总是先打印、TaskB 紧随其后。 两者优先级同为 1，configUSE_TIME_SLICING=1 让同优先级任务按时间片轮转；又因为 A 先创建、先就绪，每轮调度总是 A 先上场。

现象 3：tick 每 1000 次出头一跳，但每秒增量并不精确。 1024-2=1022，2042-1024=1018……按 1ms 一个 tick，理论上每秒应该恰好 +1000。多出来的十几毫秒就是 Windows 调度的抖动。记住这个细节：它直观地证明了”仿真环境不适合评估实时性”——如果这 20ms 的偏差发生在电机控制里，就是第一篇说的”错过 deadline”。

七、踩坑记录

  1. **任务函数绝不能 return**。返回后的行为未定义，内核甚至可能直接断言崩溃。要”结束”一个任务，标准姿势是 vTaskDelete(NULL)。
  2. **vTaskStartScheduler() 后面别写”善后代码”**。正常流程它永不返回；返回只意味着启动失败（通常是堆不足）。要检查错误，检查的是每个 xTaskCreate 的返回值。
  3. printf 不是线程安全的。两个任务同时 printf，输出可能交叉撕裂。本例频率低、单行短，问题不明显；正式产品里应该用队列把日志发给专门的”日志任务”，或用互斥量保护——这正是第 5、7 篇的主角。
  4. 别在仿真里测实时性能。tick 有抖动、调度有毫秒级延迟，量出来的数字没有参考意义。仿真学机制，真机调性能。
  5. 杀毒软件偶尔拦未签名 exe。编译出的演示程序被 SmartScreen/杀软误报时，加白名单即可。

八、小结与下一篇预告

本篇我们：

  • 理解了 Windows 仿真的原理：任务=Win32 线程，tick=定时器模拟中断；

  • 掌握了本系列最重要的两个 API：xTaskCreate 和 vTaskDelay；
  • 从真实输出里看穿了时间片轮转与调度抖动。
