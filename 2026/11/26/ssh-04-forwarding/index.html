SSH 学习笔记（四）：端口转发，-L / -R / -D 到底转发的是什么

连上一台服务器之后，SSH 能干的远不止敲命令。它还能在加密通道里”搬运”端口：把内网才有的服务搬到本地访问，把本地服务暴露到远程，甚至开一个代理让所有流量从远程出去。这就是端口转发，三个参数 -L、-R、-D 经常被背下来却没真正理解。

这一篇不背概念，直接在本机起靶机，把三种转发各跑一遍，用 curl 验证每一条隧道真的通了，再从 -vvv 日志里看清楚每种转发到底是谁在监听端口、谁去连目标。

一、先搭一个能验证转发的靶机

要验证”转发通不通”，得有一个可访问的 HTTP 服务当目标，再用 curl 从另一端去够它。靶机长这样：

  • sshd：便携版 Win32-OpenSSH，监听 127.0.0.1:2222，开 AllowTcpForwarding yes、GatewayPorts no
  • HTTP 服务：Python 起一个极简服务在 127.0.0.1:8080，任何请求都返回标识串 FWD-HTTP-8080-HELLO
  • 客户端：Windows 自带 OpenSSH，密钥指纹 SHA256:8PlD/ORyLMYPki+Oq/BqdXmKF5zxU4m4gwTmfQgu28c

先确认基线——直连 HTTP 8080 是通的：

下面三个场景，我都把 ssh 转发进程挂在后台（-N 表示不执行远程命令，只建隧道），然后用 curl 去打对应端口，看能不能拿到 FWD-HTTP-8080-HELLO。

二、三种转发，一张图看懂

一句话先记住区别：

  • -L 本地转发：在本地监听一个端口，有连接就经隧道让服务端去连目标——把远程服务”搬”到本地。
  • -R 远程转发：让服务端监听一个端口，有连接就经隧道让客户端去连目标——把本地服务”暴露”到远程。
  • -D 动态转发：在本地开一个 SOCKS 代理，目标地址由每个请求动态决定——最灵活。

下面逐个实测。

三、-L 本地转发：把远程服务搬到本地

含义：在客户端本地监听 18888，凡是连到 18888 的流量，都经 SSH 隧道送到服务端，由服务端去连 127.0.0.1:8080（注意这个 127.0.0.1 是服务端视角的本机）。

curl 验证：

访问本地的 18888，拿到了远程 8080 的内容。隧道通了。

客户端 -vvv 日志里的关键行：

流程是：客户端在本地监听 18888 → curl 连进来 → 客户端向服务端发一个 direct-tcpip 通道请求（目标 127.0.0.1:8080）→ 服务端建立到目标的连接 → 两端桥接。

典型用途：远程服务器上跑着一个只监听 127.0.0.1 的内部服务（比如数据库面板、Jupyter），本地 ssh -L 8888:127.0.0.1:8080 server 后，浏览器打开 localhost:8888 就能访问，服务本身完全不暴露公网。

四、-R 远程转发：把本地服务暴露到远程

含义反过来：让服务端监听 19999，凡是连到服务端 19999 的流量，都经隧道送回客户端，由客户端去连 127.0.0.1:8080（这次的 127.0.0.1 是客户端视角的本机）。

curl 验证（去服务端那侧打 19999，本机靶机里服务端也是本机，所以直接 curl 127.0.0.1:19999）：

远程的 19999 拿到了本地 8080 的内容。

客户端日志的关键词变成了 forwarded-tcpip（注意和 -L 的 direct-tcpip 不同）：

区别在于方向：-L 是客户端主动向服务端发 direct-tcpip；-R 是服务端主动向客户端发 forwarded-tcpip（因为远程端口有连接进来了），客户端再去连本地目标。

一个常见限制：默认 GatewayPorts no，服务端只把 -R 的端口绑在 127.0.0.1，只有服务端本机能够访问。要让其他机器也能访问远程转发的端口，需要服务端设 GatewayPorts yes（或 clientspecified），这是个安全开关，别随便开。

典型用途：本地开发的 Web 服务想让外网临时预览（没有公网 IP），在一台有公网 IP 的云主机上 ssh -R 8080:127.0.0.1:3000 cloud，访问云主机的 8080 就等于访问本地 3000——这就是各种”内网穿透”工具的底层原理之一。

五、-D 动态转发：开一个 SOCKS 代理

含义：在客户端本地监听 11080，作为一个 SOCKS5 代理。应用把流量交给这个代理，目标地址由每个请求自己决定，ssh 动态解析后经隧道从服务端发出去。

curl 验证（让 curl 走这个 SOCKS 代理去访问 8080）：

日志里能看到完整的 SOCKS5 握手过程：

通道类型是 dynamic-tcpip，先完成 SOCKS5 握手（decode socks5 → socks5 auth done → socks5 post auth），从请求里解析出目标 host 127.0.0.1 port 8080，再建隧道。和 -L/-R 目标地址写死不同，-D 的目标是每个请求临时决定的。

典型用途：浏览器装个 SwitchyOmega，把流量走 127.0.0.1:11080 的 SOCKS5，就能以远程服务器的网络出口访问内网资源或特定站点；命令行里 curl --socks5、git 配 core.gitProxy 也都能用。

六、三种转发对比

-L 本地转发 -R 远程转发 -D 动态转发
谁监听端口 客户端本地 服务端远程 客户端本地
目标地址 写死在参数里 写死在参数里 每个请求动态决定
通道类型 direct-tcpip（客户端发起） forwarded-tcpip（服务端发起） dynamic-tcpip
一句话 远程服务搬本地 本地服务暴露远程 本地开 SOCKS 代理
典型场景 访问内网面板/数据库 内网穿透、临时外网预览 浏览器/命令行走代理出口

七、踩坑记录

  1. **转发建不起来，优先加 -v 看 ExitOnForwardFailure**：默认 ssh 即使转发失败也会继续登录，让人误以为成功。加 -o ExitOnForwardFailure=yes，转发端口被占或没权限时直接退出，省得在”连上了但用不了”里绕圈。
  2. -N 别忘：只做转发不执行命令时加 -N，否则 ssh 会开一个 shell，看着像卡住；后台跑再加 -f（fork 到后台）。
  3. -R 的端口只能服务端本机访问：默认 GatewayPorts no，远程转发绑在 127.0.0.1。要让外网访问需服务端改 GatewayPorts，这是安全决策，不是 bug。
  4. -D 是 SOCKS5，不是 HTTP 代理：浏览器要选 SOCKS5，curl 用 --socks5（或 --socks5-hostname 让远程解析 DNS），配错代理类型会直接连不上。
  5. 靶机里的目标 127.0.0.1 视角要分清：-L 的目标是服务端的本机，-R 的目标是客户端的本机。本篇两端都是同一台机器，所以 curl 都能打到；换成真实两台机器时，写错 IP 就会”curl 通了但内容不对”。
  6. Windows 上杀 ssh 进程看 exit code 会误导：本篇验证完用 taskkill 终止转发进程，ssh 显示 exit 1，这不代表失败——curl 已经在转发存活期间拿到了 200。判断转发是否成功看 curl 的 http_code，别只看 ssh 的退出码。

八、小结与下一篇预告

三句话收尾：

  • **-L 是”远程搬本地”**：客户端监听，发 direct-tcpip，服务端连目标，用于访问内网服务。
  • **-R 是”本地暴露远程”**：服务端监听，发 forwarded-tcpip，客户端连目标，用于内网穿透。
  • **-D 是”本地 SOCKS 代理”**：动态解析目标，走 dynamic-tcpip，灵活但需要应用支持 SOCKS5。
