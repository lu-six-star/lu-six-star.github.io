SSH 学习笔记（一）：一次 ssh 登录到底发生了什么

每天敲 ssh user@host，回车之后一两秒就进去了。敲得多了，容易把 SSH 想成”加密版的 telnet”——反正就是连上、输密码、干活。可一旦报错：Permission denied、Host key verification failed、私钥”权限太开放”被拒绝加载——脑子里没有一张图，就只能靠搜关键词碰运气。

所以这个系列第一篇不背命令，而是把一次登录从头到尾跑一遍：在本机起一个真实的 SSH 服务端，给客户端加上 -vvv，让它把每一步都喊出来。文中出现的指纹、字节数、耗时、报错，全部是本机实测抓的，不是抄的。

一、先搭一个”能看见全程”的靶机

1.1 为什么不直接连一台云服务器

看握手过程，-vvv 是基本操作。但更关键的是：我想观察认证失败和主机密钥被换掉这两种场景，总不能真去动生产服务器。所以这次在本机造一个靶机——用 Python 3.12 + paramiko 5.1.0 写一个最小 SSH 服务端，监听 127.0.0.1:2222；客户端就用 Windows 自带的 OpenSSH。

有一件事必须先讲清楚：服务端是 paramiko 实现，不是 Linux 上的 OpenSSH sshd，所以日志里会出现 remote software version paramiko_5.1.0。但版本串、KEXINIT 算法清单、密钥交换、用户认证、通道申请——这些都是 SSH 协议本身规定的报文，两边讲的是同一套协议。换成一台真实的 Linux 服务器，变化的只是 banner 文字和算法偏好的顺序，握手的流程一步都不会少。

1.3 服务端只有三十行核心逻辑

paramiko 的服务端骨架薄得像张纸：加载主机私钥 → 起监听 → 每个连接起一个 Transport → 在回调里回答”这个密码 / 这把公钥行不行”。

客户端连通后执行 hostname & whoami & echo SSH-LAB-OK，服务端用 cmd.exe /c 真跑，再把 stdout 和 exit-status 回送。完整的实验代码和全部原始日志都在 ssh-lab/ 里。

二、原理：六步走完一次登录

把 -vvv 日志按阶段切开，一次登录其实就干了六件事：

阶段 干什么 此时数据是明文吗
① TCP 连接 三次握手，连上 22（这里是 2222）端口 是
② 版本交换 双方各报一句 SSH-2.0-xxx，只报身份不做认证 是
③ 算法协商 各发一张 KEXINIT 清单（KEX / 主机密钥 / 加密 / MAC），取交集 是
④ 密钥交换 ECDH 算出会话密钥；服务器用主机私钥签名，证明”我是这台机器” 开始混合
⑤ 切换加密 NEWKEYS 之后，所有报文走对称加密 否
⑥ 用户认证 客户端声明公钥 + 用私钥签名，服务器在白名单里验证 否（加密通道内）

六步走完，才轮到 session 通道、exec 请求、回传 stdout 和退出码。

有一个结论值得钉在最前面：登录密码（或私钥）从来不”传”给服务器，它是在已经加密的通道里被验证的——这正是 SSH 和 telnet 的根本区别。telnet 是把口令明文送过去，SSH 是先把通道锁死，再在锁里验明正身。

三、实测：逐段读 -vvv 日志

3.1 版本交换：先互相报名

这一步是明文的。任何中间人都能看到”你在连哪台机器、对方跑的是什么软件”。也正因为它必须明文，SSH 才背上了历史包袱：有些老服务器会傻等版本串、有些实现的 banner 格式不规范，于是客户端积累了一堆 compat_banner 兼容规则——no match 只是说”没触发任何已知的兼容补丁”，不是报错。

3.2 算法协商：不是客户端说了算，是取交集

服务器也回一张（节选）：

三个细节，全是这次真实协商出来的，值得停下来看一眼：

  1. **客户端首选 chacha20-poly1305@openssh.com，最后却用了 aes128-ctr**——因为服务端（paramiko）的清单里根本没有 chacha20。算法的选择规则是”取客户端清单中、服务端也支持的第一项”，所以换一台服务器，这里用的密很可能就变了。
  2. 服务端其实提供了 mlkem768x25519-sha256（后量子混合密钥交换），但客户端 9.5 不认识它，只好退回到 curve25519-sha256@libssh.org。协议的双向兼容就是这么工作的：谁都别想单方面升级，得两边都点头才算数。
  3. **will use strict KEX ordering**：双方都支持 kex-strict-* 扩展，于是启用了严格 KEX 顺序，堵掉了 Terrapin 那类”在握手报文里动手脚”的攻击面。

3.3 密钥交换：主机密钥出场

这一步同时发生了两件事，别混为一谈：

  • 双方用 ECDH 各自算出同一份会话密钥——密钥本身不在网络上传输，只交换临时公钥；
  • 服务器额外用主机私钥对整个握手数据签名，客户端拿 known_hosts 里存的主机公钥来验签。

验签通过，客户端才敢确认”对面确实是上次那台机器”。注意 [127.0.0.1]:2222 这种写法——端口不是默认的 22 时，known_hosts 的条目会带上端口，这也是为什么改了端口之后，客户端会”重新问一次 yes”。

3.4 用户认证：先问一句，再交签名

公钥认证是两轮的：

  • 第一轮，客户端先发公钥问一句”这把钥匙你认不认”，服务器回 type 60（PK_OK）表示”认，你可以用它签名”；
  • 第二轮，客户端才用私钥对会话数据签名、正式提交，服务器回 type 52 表示认证成功。

所以去看服务端日志，会发现 auth PUBLICKEY accepted 出现了两次——这不是 bug，是协议规定的两轮。

很多人以为”公钥登录就是把公钥发给服务器校验一下”，其实服务器从头到尾只做一件事：用你提供的公钥，验证你用对应私钥做出的签名。私钥从始至终没离开过本机。

六、耗时实测：握手到底占多少

本机回环，连续 5 次”连接 + 认证 + 执行 echo tick“的端到端耗时：

平均约 132 ms，波动 123~146 ms。这个数字里包含了进程启动、DLL 加载、握手、认证、通道建立和命令执行——回环网络本身几乎不花时间，所以它基本就是”SSH 客户端本身的固定开销”。

这也解释了为什么连远程服务器感觉慢得多：真正的成本是 RTT × 握手往返次数。从一个 30 ms 延迟的机房连过去，光握手就要跑好几个 RTT，这是物理距离决定的，跟加密算法关系不大（curve25519 的运算在微秒级）。

七、踩坑记录

  1. 私钥权限：Windows 上用 icacls 收 ACL，Linux 上 chmod 600；从别处拷来的私钥几乎必然踩坑（本篇 5.1 现场）。
  2. 中文路径不影响 SSH，但会把日志搞花：博客 在 -vvv 里显示成 \345\215\232\345\256\242，那只是 UTF-8 的八进制转义，文件读取完全正常，不必改目录名。
  3. 服务端认证回调会被调用两次：第一次是”公钥查询”（不带签名），第二次才是带签名的正式认证。写自己的 SSH 服务端时，别把第一次当成”登录成功”。
  4. no channel opened 不是网络故障：客户端在认证阶段就退出（比如权限问题、公钥被拒），自然不会开 session 通道；服务端等 20 秒超时后才打印这句。
  5. known_hosts 不是授权文件：它只回答”这台服务器是不是上次那台”，跟”我能不能登录”毫无关系。把两者搞混，就会在”明明密钥配好了却连不上”里绕圈。
  6. 非 22 端口要带方括号：[host]:port 是 known_hosts 和 ssh-keygen -R 的标准写法，漏了括号会删不掉条目。

八、小结与下一篇预告

三句话收尾：

  • 握手六步：TCP → 版本 → 算法协商（取交集）→ 密钥交换（主机密钥签名）→ NEWKEYS → 用户认证；之后才是通道和命令。
  • 两把钥匙分工明确：host key 证明”机器是谁”，user key 证明”人是谁”；私钥永不出本机，公钥分别进 known_hosts 和 authorized_keys。
  • 绝大多数登录失败只有三类：私钥没被加载（权限）、主机身份对不上（known_hosts）、公钥不在白名单（authorized_keys）。-vvv 一眼就能分清。
