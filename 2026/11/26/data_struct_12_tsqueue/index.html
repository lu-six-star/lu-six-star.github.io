数据结构（十二）：手写线程安全队列 —— 竞态与临界区

系列压轴：把第 7 篇的链表队列搬进 FreeRTOS 多任务环境——两个任务同时操作队列会发生什么？答案是竞态：读-改-写三步被打断，数据丢失。解法是临界区保护。本篇真机实测：手写队列（临界区保护）与内置 xQueue 各收发 500 条，双双零丢失、顺序完全正确。

一、竞态：三步操作被打断的灾难

链表入队是”读-改-写”三步：读 tail → 挂新节点 → 改 tail。两个任务同时入队：

  1. 任务 A 读到 tail = 节点 3；
  2. 任务 A 尚未改 tail，被切走；
  3. 任务 B 也读到 tail = 节点 3，挂上自己的节点，tail = B；
  4. 任务 A 恢复，把自己的节点挂在过时的 tail（节点 3）上，tail = A——B 的节点从链上脱落，数据丢失。

这就是竞态（race condition）：结果取决于任务切换的时机，每跑一次都可能不同——比必现 bug 更难抓。

四、手写 vs 内置：该用哪个

维度 手写队列（临界区） 内置 xQueue
正确性 实测零丢失 ✓ 零丢失 ✓
阻塞语义 要自己做（本例用 taskYIELD 轮询） 满/空自动阻塞唤醒（第 5 篇实验 7）
优先级继承/等待列表 没有 内置
定制自由度 完全自由 受 API 限制

结论清晰：生产环境用内置 xQueue——它就是”链式队列 + 阻塞唤醒 + 临界区保护”的封装。手写的意义在于：读懂了它，你就读懂了 xQueue 的骨架；也让你在”内置队列不满足需求的特殊场景”（如超轻量中断缓冲）有能力自己造轮子。

五、踩坑记录

  1. 临界区里调 malloc/free——本实验这样做是安全的（Win32 临界区是真正的互斥窗口），但严格来说要保证 malloc 实现的线程安全；确定性的写法是预分配节点池；
  2. 临界区越短越好——窗口内做重活，所有任务都会被卡住；只放”改指针”这几条指令；
  3. volatile 不等于线程安全——volatile int iQCount 只防编译器优化，不防竞态；该临界区还得临界区；
  4. 轮询 vs 阻塞——本实验消费者用 taskYIELD 轮询空队列，浪费 CPU；工程上用事件组/任务通知让”队列有货”事件驱动（第 8 篇）。
