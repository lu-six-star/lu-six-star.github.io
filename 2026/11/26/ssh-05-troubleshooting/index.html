SSH 学习笔记（五）：登录故障排查清单，从 -vvv 日志一眼定位

这是系列收尾。前四篇把登录的每一层都跑了一遍，也踩了一串真实的坑：私钥被拒收、主机密钥对不上、公钥不在白名单、config 优先级写错、跳板连不上、转发建不起来。它们在终端里的长相高度相似——一句 Permission denied，或者一段 Connection timed out——但根因完全不同，修法也完全不同。

这一篇把这些故障按 -vvv 日志的阶段重新整理成一张可逐条对照的清单：看到哪一行日志，基本就能锁定是哪一层出了问题，该去查哪个文件、跑哪条命令。清单里所有报错片段都来自本系列的真实实验日志。

一、先记住：一次登录分五层，每层都会失败

ssh -vvv 会把连接过程按顺序喊出来，失败发生在哪一层，日志就停在哪一层。从外到内五层是：

报错定位的核心思路：看日志最后停在哪一步。停在 ① 是网络/端口，停在 ③ 是 known_hosts，停在 ④ 是密钥或 authorized_keys，停在 ⑤ 是通道或命令。下面按层整理。

二、逐层排查清单

2.1 第 ① 层：连都连不上

现象

或 Connection timed out，或 -vvv 卡在 Connecting to ... port 22 之后没有任何下文。

根因：TCP 都没通。常见三类：服务没起、端口写错、被防火墙挡了。

怎么查

Connection refused 说明端口没在听（服务没起或端口错）；timed out 说明包被丢了（防火墙 / 安全组 / 路由）。

本系列里我第一次跑 paramiko 靶机时漏了 start_server，客户端连上去立刻被 reset，就是这一层——TCP 握手成了但应用层没接，日志停在版本交换之前。

2.2 第 ③ 层：主机密钥对不上

现象

根因：服务器发来的主机密钥指纹，和客户端 known_hosts 里记录的对不上。要么真换了机器 / 重装系统，要么有人在中间（中间人）。

怎么修：先通过带外渠道核对新指纹，确认是合法变更，再删旧条目重连：

不核对就删，等于把中间人告警一键静音。这个告警存在的唯一意义就是逼你停下来核对。

另一种第 ③ 层报错是第一次连时的交互确认：

非交互脚本里要预先 ssh-keyscan 把主机公钥写进 known_hosts，或用 StrictHostKeyChecking accept-new（仅可信内网）。

2.3 第 ④ 层：认证失败——私钥根本没被加载

现象

根因：不是”认证被拒”，而是客户端在加载阶段就把这把私钥判为不安全、直接忽略了——根本没把钥匙掏出来。从别处拷来的私钥几乎必踩。

怎么修

判断技巧：-vvv 里如果看到 Load key "...": bad permissions 或 This private key will be ignored，就是这层的问题，别去查服务端。

2.4 第 ④ 层：认证失败——公钥不在白名单 / 被选项拦截

现象

根因：私钥正常加载了（能看到 Offering public key），但服务端拒绝了。type 51 就是”这把不行，请换一种”。常见三种：

  1. 公钥没写进服务端的 ~/.ssh/authorized_keys（最常见）。
  2. 写进去了但权限或属主不对——StrictModes yes 时，authorized_keys 或 .ssh 目录权限过宽、属主不是登录用户，sshd 会直接忽略整个文件。
  3. 公钥在白名单，但行首选项把你拦了（第二篇实测）：

怎么查：去服务端看 sshd 日志（/var/log/auth.log 或 journalctl -u sshd；Windows 便携版用 -E 指定日志文件），找 Accepted 还是 refused、Authentication refused: bad ownership or modes、forced command 这类行，一眼分清是没写进去、权限错了、还是被选项限制了。

三句话自检：公钥真写进 authorized_keys 了吗？目录和文件权限对吗？服务端 PubkeyAuthentication yes 吗？三句任何一句不成立，看到的都是同一句 Permission denied。

2.5 第 ④ 层：config 把你带沟里了

现象：明明密钥、白名单都对，但 ssh lab 就是连不上；换个写法又好了。

根因：~/.ssh/config 的解析结果和你以为的不一样。最典型的就是第三篇的 Host * 位置错误——单值参数 first-match-wins，Host * 写在前面会抢在具体 Host 之前命中，导致 port、user 全错。

怎么查：先跑 ssh -G，别先连：

看解析出的 port 是不是你要的、identityfile 指对没有、proxyjump 有没有生效。很多”连不上”在这一步就露馅了。

2.6 第 ④~⑤ 层之间：跳板机连不上

现象：用了 ProxyJump 后报错：

或 jump 能登、target 却 Connection closed by remote host。

根因（本系列实测踩过）：ProxyJump 的子连接（连跳板的那个 ssh 进程）不继承命令行的 -o 选项。你在命令行写了 -o UserKnownHostsFile=xxx，只对主连接 target 生效；连 jump 的子进程读的是 config 里的默认值，去读 ~/.ssh/known_hosts，找不到 jump 的主机密钥就卡住，隧道里 target 的 banner 永远收不到。

怎么修：把 UserKnownHostsFile、StrictHostKeyChecking、BatchMode 这些通用选项写进 config 的 Host * 块，不要只写在命令行。跳板本身的配置（jump 的 HostName/Port/IdentityFile）也要在 config 里完整，否则第一段就过不去。

判断技巧：-vvv 里找有没有 Authenticated to ... (via proxy)。有这行说明跳板通了、问题在 target；没有这行，问题在 jump 这第一段。

2.7 第 ⑤ 层：转发建不起来

现象：ssh -L/-R/-D 连上了，但本地/远程端口访问不了，curl 超时。

怎么查：先加 -o ExitOnForwardFailure=yes，让转发失败时 ssh 直接退出，而不是静默登录成功却没有隧道。然后看 -vvv 里有没有：

  • Local forwarding listening on ... / remote forward success：转发建立成功，问题在应用端（代理类型写错、目标 IP 视角错）。
  • bind: Address already in use：端口被占，换一个。
  • 没有任何 forward 相关日志：服务端 AllowTcpForwarding no 禁了，或 GatewayPorts 限制了 -R 的监听地址。

第四篇实测：-L 成功时日志有 channel N: new [direct-tcpip]，-R 是 forwarded-tcpip，-D 是 dynamic-tcpip——看不到对应通道类型，转发就没真正建立。

三、一张决策速查表

你在日志里看到 大概率卡在 先查 / 先跑
Connection refused / timed out ① TCP 服务在听吗、端口对吗、防火墙
REMOTE HOST IDENTIFICATION HAS CHANGED ③ 主机密钥 核对指纹后 ssh-keygen -R
Host key verification failed ③ 主机密钥 known_hosts 里有没有这台
UNPROTECTED PRIVATE KEY FILE / will be ignored / bad permissions ④ 私钥加载 chmod 600 或 icacls 收权限
Offering public key + type 51 + Permission denied ④ 公钥认证 authorized_keys 写了吗、权限对吗、选项拦了吗
ssh -G 解析出的 port/user 和预期不符 ④ config Host * 是否写在了前面
banner exchange 超时 / 没有 (via proxy) ④ 跳板 通用选项是否写进了 config 的 Host *
转发连上但端口不通、无 direct/forwarded/dynamic-tcpip ⑤ 转发 加 ExitOnForwardFailure=yes，查 AllowTcpForwarding

四、从外到内的排查流程

遇到问题别上来就改配置，按这个顺序走，基本五分钟内定位：

  1. 先看 TCP：ssh -v 有没有进到 Connecting to ... port。没有下文 → 网络/端口/服务问题（第 2.1 节）。
  2. 看主机密钥：有没有 Host key verification failed 或 IDENTIFICATION HAS CHANGED。有 → known_hosts 问题（第 2.2 节）。
  3. 看私钥加载：-vvv 里找 Offering public key。没有 → 私钥没加载，查权限（第 2.3 节）；有 Load key ... bad permissions 直接锁定。
  4. 看服务端回应：Offering public key 之后收到 type 51 → 服务端拒绝，查 authorized_keys / 权限 / 选项（第 2.4 节）。这时去看服务端 sshd 日志最有效。
  5. 看 config：以上都正常却连不上，ssh -G 打印最终配置，对照预期（第 2.5 节）。
  6. 看场景：用了跳板查第 2.6 节，用了转发查第 2.7 节。

这个顺序的好处是：每一步只需要看日志的一个片段，不用通读几千行 -vvv 输出。

五、小结：这个系列到底交付了什么

五篇连起来，是一条从”知其然”到”知其所以然”再到”出问题能自己查”的完整路径：

  • 第一篇：把一次登录拆成六层，用 -vvv 看见每一步，区分 host key 和 user key、known_hosts 和 authorized_keys。
  • 第二篇：把免密登录跑通，讲清 authorized_keys 的行首选项（限制命令、限制来源）和 ssh-agent 如何一把钥匙开多台机器。
  • 第三篇：把一长串参数收进 config，搞懂 first-match-wins，用 ProxyJump 一步过跳板。
  • 第四篇：用 -L/-R/-D 开隧道，从日志里看清每种转发是谁在监听、谁在连目标。
  • 第五篇（本篇）：把前四篇的坑汇总成按阶段定位的排查清单，遇到报错不再靠搜关键词碰运气。

SSH 看起来就是”加密版 telnet”，但真正把它用顺、出问题能自己搞定，靠的是脑子里有这张分层的图。希望这五篇能帮你把这张图建起来。
