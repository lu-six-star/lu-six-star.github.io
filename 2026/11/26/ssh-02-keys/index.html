SSH 学习笔记（二）：authorized_keys 的门禁、ssh-agent 与真正的免密登录

上一篇把一次登录从头到尾跑了一遍，最后配好了公钥登录。但真把公钥登录用起来，问题才刚开始：这把钥匙能不能只管一件事——比如只允许跑 rsync、不许开 shell？能不能只允许某台机器用它？私钥设了 passphrase 之后，难道每次都要输一遍？

这些问题的答案，全部藏在 authorized_keys 那一行文本里，以及一个叫 ssh-agent 的小进程里。本篇继续用同一套本机靶机，5 个场景 + 1 组 agent 实验，全部实测。

一、痛点：免密登录之后的三道新问题

上一篇结束时，服务端的 authorized_keys 里躺着一行公钥，客户端 ssh -i key chris@host 就能直接进去，不输密码。看起来”免密”已经完成了，但实际部署时会立刻遇到三个问题：

第一，权限太大。 我把公钥放进服务器，就等于给了对方一个完整 shell。可我的需求可能只是”让备份脚本能 rsync 一份目录”。万一这行公钥对应的私钥泄露，攻击者拿到的是完整控制权，不是一条只读命令。

第二，来源不受控。 同一把钥匙，昨天在一台办公机上用，今天被拷到别的地方也能用。能不能限定”只允许来自 10.0.0.0/8 的连接”？

第三，passphrase 与便利性冲突。 给私钥加了口令，安全性很好，但每次登录都要输一遍——自动化脚本就直接卡死了。这正是 ssh-agent 存在的理由。

这三个问题，前两个由 authorized_keys 的行首选项解决，第三个由 ssh-agent 解决。

二、原理：authorized_keys 不是一行公钥，而是一条规则

很多人以为 authorized_keys 就是把 .pub 文件内容粘进去。其实每一行都是一个完整的规则：

只有中间的”算法 + 公钥”是必填的，前面的选项和后面的注释都可省略。sshd 收到连接后，会把客户端出示的公钥指纹逐行比对；一旦在某一行的公钥上命中，就按这一行行首的选项来处理后续，而不是继续往下找。

常用选项速查：

选项 作用 典型场景
command="..." 强制用指定命令替换客户端请求的命令 只允许备份 / 只允许查询
from="..." 只接受指定来源（IP、网段、域名，逗号分隔） 限定办公网、限定固定跳板机
no-pty 不分配伪终端，禁止交互式 shell 纯自动化账号
no-port-forwarding 禁止端口转发 收紧权限
no-agent-forwarding 禁止 agent 转发 防止钥匙被借道
restrict 关掉以上所有”额外能力”（新版推荐） 最严格基线

一个值得记住的细节：选项里的引号和逗号是有语法意义的，command="a,b" 和 command="a",command="b" 完全不是一回事。写错就直接拒绝加载整行。

三、准备：一台便携版 sshd 和四把钥匙

这次不用 paramiko 模拟，直接拿 Win32-OpenSSH 便携版（OpenSSH_for_Windows_9.5p1, LibreSSL 3.8.2）在本机起一个真实 sshd，监听 127.0.0.1:2222。这样 authorized_keys 的解析、日志、拒绝原因，全都是 OpenSSH 服务端的原生行为，不是我自己模拟出来的。

两个说明：

  • PasswordAuthentication no——把密码通道关掉，逼着只能走公钥，这样每个场景成没成功，只取决于公钥这一条路径。
  • StrictModes no——Windows 的 ACL 检查在实验目录里容易误伤（目录被 Users 组可读），先关掉；**生产环境应该保持默认的 yes**，让 sshd 去校验 authorized_keys 和家目录的属主权限。

这里有个真实世界里极易踩的坑：**from= 校验的是 sshd 看到的对端地址。如果你的连接经过了 NAT、负载均衡或者跳板机，那 sshd 看到的是上一跳的地址**，不是你的原始 IP。服务器前面挂了 LB，所有人的来源都会变成 LB 的内网 IP，from= 就等于失效了。这种场景要看 sshd_config 里的 UseDNS、X11Forwarding 之类的转发头配置，或者干脆改用证书认证做来源控制。

五、ssh-agent：私钥不离开 agent，要签名就喊它

5.1 它到底解决什么问题

给私钥加 passphrase 是好事——私钥文件被拷走也用不了。但代价是每次登录都要输。ssh-agent 的思路很干净：私钥解密一次，放进 agent 的内存里，之后所有签名请求都交给 agent 做。私钥本身不再落到磁盘上被读取，也不需要在每条命令里 -i 指定。

它的协议很窄，只有几个动作：

动作 谁发起 干什么
ssh-add <key> 用户 解密私钥、把私钥交给 agent 保管
ssh-add -l 用户 列出 agent 里有哪些公钥（指纹）
ssh-add -D 用户 清空全部
签名请求 ssh 客户端 客户端只说”用这把公钥签个名”，签名由 agent 完成

关键在于最后的签名请求：客户端从头到尾没有读过私钥文件，它只拿着一份公钥清单去问 agent”你能不能签”。这就是为什么 agent 里的钥匙能同时服务十台服务器——十台机器的 authorized_keys 里放着同一把公钥，客户端只要在 agent 里签一次。

5.4 一个真实的反向坑：IdentitiesOnly=yes 会把 agent 屏蔽掉

我第一次跑这个实验时，顺手沿用了 4.x 节的 -o IdentitiesOnly=yes，心想”这样更严谨，只让 agent 提供”。结果连接失败，服务端日志显示客户端 offer 的是一把 RSA 钥匙：

而 agent 里明明躺着 ED25519。翻了 man ssh_config 才明白：

IdentitiesOnly — Specifies that ssh should only use the authentication identity and certificate files explicitly configured in the ssh_config files or passed on the ssh command-line, even if ssh-agent offers more identities.

也就是说，IdentitiesOnly=yes 的”only”指的是”only 配置文件/命令行里的”，它会把 agent 里的钥匙排除在外。这个选项的正确用途是”我指定了 -i，不要让客户端再拿 agent 里的钥匙去乱试”，而不是”让客户端只用 agent”。

去掉它之后，第三节的 -v 日志立刻变成 Will attempt key: ... agent，登录成功。

七、踩坑记录

  1. IdentitiesOnly=yes 与 agent 互斥：它只认配置文件和命令行里的 IdentityFile，会忽略 agent。带 -i 时用它防乱试是对的；想让 agent 生效，就必须去掉。
  2. Windows 的 agent 是服务，不是进程：便携版 ssh-agent.exe 会去拉系统服务，服务 Disabled 时报 error :1058；ssh-add 报 Error connecting to agent: Permission denied 或 No such file or directory，都先查 Get-Service ssh-agent。
  3. ssh-add -l 退出码是 1 不等于出错：agent 空的时候它返回 1 并打印 The agent has no identities.，写脚本时别把这种情况当失败。
  4. from= 看的是 sshd 视角的对端地址：前面有 NAT / LB / 跳板时，看到的是上一跳 IP，原始来源会被抹掉。
  5. 客户端报错无法区分失败原因：”公钥不在白名单”和”来源不被允许”在客户端都是 Permission denied (publickey,keyboard-interactive)，必须看服务端日志里的 correct key but not from a permitted host。
  6. command= 不是万能锁：它替换的是客户端的请求，被强制的那条命令如果自己能读参数、能起子进程，限制就被绕过了。真正的限制要靠”命令本身不接受外部输入”。
  7. StrictModes no 只为实验方便：Windows 上 ACL 检查容易把实验目录判为不安全。生产环境保持默认 yes，并确保 authorized_keys 属于对应用户、其他用户不可写。

八、小结与下一篇预告

三句话收尾：

  • authorized_keys 的每一行是一条规则：[选项] 算法 公钥 注释。命中哪一行，就按哪一行的选项走；command= 换掉你要执行的命令，from= 卡住你的来源地址。
  • **ssh-agent 把”私钥文件”换成”内存里的签名服务”**：加载一次，多台机器共用；日志里 ... agent 后缀就是它出手的标志。Windows 上它是系统服务，管好 Get-Service ssh-agent。
  • 免密失败的排查顺序：钥匙进没进 agent → 指纹对不对 → 服务端有没有这行 → 来源选项拦没拦。客户端报错永远只是”Permission denied”，答案在服务端日志里。

到这里，免密登录是真正跑通了。但命令也变长了：ssh -i ... -p 2222 -o ... Chris@127.0.0.1。下一篇把这些参数收进 ~/.ssh/config，让一条 ssh lab 搞定，并顺手用 ProxyJump 打通”本机 → 跳板机 → 内网机器”的链路。同样全部本机实测，ssh -G 的解析结果和跳板机日志都会贴出来。
